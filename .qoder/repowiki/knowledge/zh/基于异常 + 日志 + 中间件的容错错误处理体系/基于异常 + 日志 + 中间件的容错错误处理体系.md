## 1. 整体方法

本仓库没有自定义的领域级 `Exception` 类型，也没有统一的错误码枚举。错误处理采用 **三层组合**：

- **调用方契约层**：大量 API / 命令方法通过 `TryXxx(out string message)` 形式返回布尔值并附带人类可读的错误消息（如 `TryWriteRackControlRegister`、`TryAuthorize`、`TryListTests`），由调用方决定是记录警告还是返回 HTTP 400/403。
- **运行时异常层**：在参数校验、状态不一致等“不应发生”的场景直接抛出标准 .NET 异常（`ArgumentNullException`、`ArgumentOutOfRangeException`、`InvalidOperationException`、`FileNotFoundException` 等），例如 `EssDeviceSimModel/Devices/GridSimulator.cs`、`PcsDevice.Core.cs`、`ThermalNetwork.cs`、`Program.cs` 中加载配置文件失败时。
- **外围边界层**：所有与外部系统交互的循环（遥测轮询、控制轮询、反馈轮询）以及 Modbus 从站 I/O 都被 `try/catch (Exception ex)` 包裹，统一通过 log4net 记录后继续运行，避免单点故障拖垮整个会话。

Web 层使用 ASP.NET Core 中间件进行横切错误处理：`ApiKeyAuthMiddleware` 对 `/api/*` 做可选鉴权，未配置或 Key 不匹配时直接返回 503/401 JSON；其余端点依赖 ASP.NET Core 默认全局异常处理，业务侧通过 `Results.Ok(...)` / `Results.BadRequest(...)` / `Results.NotFound(...)` / `Results.Json(..., statusCode: 403)` 显式表达成功与各类错误。

## 2. 关键文件与位置

| 层次 | 文件 | 职责 |
|---|---|---|
| 启动入口 | `Program.cs` | 配置加载失败抛 `FileNotFoundException`；授权失败写 `Console.Error` 并 `Environment.ExitCode = 2` 退出；log4net 初始化失败降级为 BasicConfigurator |
| Web 鉴权 | `Web/ApiKeyAuthMiddleware.cs` | 拦截 `/api/*`，缺失/错误 API Key 返回 401，未配置返回 503，使用固定时间比较防时序攻击 |
| Web 路由 | `Web/EndpointExtensions.cs` | 所有 REST 端点集中注册；业务错误以 `CommandResult.Fail` + `BadRequest` 或 403/404 JSON 返回 |
| 数据交换会话 | `DataExchange/DataExchangeSession.cs` | 四个后台线程（telemetry/rackTelemetry/control/feedback）各自 `try/catch(Exception)` 包裹主循环，捕获后仅记日志并 sleep |
| 控制管道 | `DataExchange/Pipeline/ControlPipeline.cs`、`ControlFeedbackPipeline.cs`、`TelemetryPipeline.cs`、`RackTelemetryPipeline.cs` | 单次执行被 try/catch 保护，防止单个点解析失败中断整批 |
| 严重告警 | `Display/FatalSystemAlert.cs` | 进程级安全事件（如黑启动联锁违规）触发事件 → SignalR 推送前端全屏告警 → 倒计时后 `Environment.Exit(1)` |
| 协议栈 | `Protocol/ModbusSlave.cs`、`ModbusHostedService.cs`、`ModbusSimServer.cs`、`ModBusParser.cs` | Modbus 读写异常、服务停止异常均 catch 后记录日志；空值写入抛 `NullReferenceException` |
| 仿真内核 | `EssDeviceSimModel/...` | 构造期参数校验抛 `ArgumentNullException`；数值越界抛 `ArgumentOutOfRangeException`；非法状态抛 `InvalidOperationException` |
| 显示命令 | `Display/CommandProcessor.cs`、`DpcAutoTestCommand.cs` | 命令执行异常被 catch 后转为 `CommandResult.Fail` 或记录日志 |

## 3. 架构约定与设计决策

1. **后台循环永不崩溃**：`DataExchangeSession` 的 telemetry/control/feedback 三个循环以及 rack telemetry 循环均以 `while(_running) { try { ... } catch(Exception ex) { _log.Error(...) } Thread.Sleep(...) }` 模式实现，确保单个设备的数据交换线程异常不会导致其他线程或进程退出。
2. **可恢复错误走 Try 模式**：需要区分“正常业务拒绝”和“异常”的场景（如找不到簇级控制点、簇索引越界、API Key 校验失败）一律提供 `TryXxx(out string message)` 重载，调用方据此返回 400/403/404 等语义化 HTTP 状态。
3. **不可恢复错误抛异常**：构造阶段参数为空、电气模型内部不变量被破坏（如 `GridSimulator` 电压 ≤ 0、PCS 在无电网时连接电网）直接抛标准异常，交由上层或宿主处理。
4. **严重安全事件走事件 + 进程退出**：`FatalSystemAlert` 是单例事件总线，首次触发后记录日志、通知订阅者（`Program.cs` 中订阅并通过 SignalR 推送到前端）、设置退出倒计时，最终调用 `Environment.Exit(1)`。该机制用于黑启动联锁等必须停机的情形。
5. **无全局异常中间件**：项目未在 `Program.cs` 中注册 `UseExceptionHandler` / `UseStatusCodePages`，因此 Web 层错误呈现依赖每个端点自行返回合适的 `IResult`，或由 ASP.NET Core 默认行为输出 HTML 错误页。
6. **日志优先于堆栈传播**：几乎所有 catch 块都通过 log4net 记录异常详情，而不是向上抛出，保证 Modbus 从站、DataExchange 会话等长驻服务的韧性。

## 4. 观察到的约束与规则

- **参数校验**：EssDeviceSimModel 各设备构造函数普遍使用 `x ?? throw new ArgumentNullException(nameof(x))` 及 `if (...) throw new ArgumentOutOfRangeException(...)`，属于构造期前置条件检查。
- **API 鉴权强制路径**：`ApiKeyAuthMiddleware` 仅在 `WebConfig.ApiKeyEnabled == true` 时生效，且豁免 `/api/health`；鉴权失败必须返回 401 或 503 JSON，不得放行。
- **致命告警幂等**：`FatalSystemAlert.Trigger` 使用 `Interlocked.CompareExchange` 保证仅首次触发有效，重复调用被忽略。
- **后端循环隔离**：`DataExchangeSession` 中 telemetry、rackTelemetry、control、feedback 四个独立线程各自 try/catch，禁止跨线程传播异常。
- **授权失败即退出**：`Program.EnforceLicenseOrExit` 在商业版/定制版缺少 license.txt 时直接 `Environment.ExitCode = 2` 终止进程，不允许带病启动。
- **HTTP 语义**：`EndpointExtensions` 中所有业务拒绝均返回明确的 `BadRequest`/`NotFound`/`Forbidden` JSON，而非抛出异常再由框架转换。

总体而言，该仓库的错误处理策略是：**核心计算路径靠异常表达不变量破坏，I/O 与协议边界靠 try/catch + 日志保持存活，Web 层靠显式 Result 表达业务错误，严重安全事件通过 `FatalSystemAlert` 事件驱动前端告警并退出进程**。
